# 第一部分：功能需求

## 1. 项目概述

"互通有无"（The Exchange）是一个 Minecraft 服务端 Mod，旨在为多个服务器之间构建**分布式物品共享空间**，让玩家可以跨服查看、放入、取出物品。

Mod 采用 **Client-Optional** 设计：

- **仅服务端安装**：玩家通过指令完成所有操作。
- **客户端同时安装**：玩家可使用 GUI 界面操作（指令仍然可用）。

核心目标：打破单服物理隔离，实现安全、可控的跨服物品流通。

## 2. 规模要求

- 支持接入服务器数量：**≤ 10 台**。
- 每台服务器的共享空间容量：**不设硬上限**，由实际存储能力约束。
- 目标 MC 版本：**1.21.11，26.1.x 为首期**，后续覆盖 1.20.x ~ 最新稳定版。
- 目标 Mod 加载器：**Fabric / Forge / NeoForge**。

## 3. 功能清单

### 3.1 服务器管理（管理员）

| 编号 | 功能 | 说明 |
|------|------|------|
| F-01 | 添加远程服务器 | 管理员通过指令添加可连接的远程服务器，需提供：地址（IP/域名）、端口、对方共享空间密码 |
| F-02 | 删除远程服务器 | 管理员通过指令移除已添加的远程服务器 |
| F-03 | 查看服务器列表 | 管理员可查看所有已配置的远程服务器及其在线状态 |
| F-04 | 配置本服信息 | 管理员可在配置文件中设定本服共享空间的显示名称和访问密码 |
| F-05 | 热重载配置 | 管理员可通过指令重载 Mod 配置，无需重启服务端 |

### 3.2 打开共享空间（所有玩家）

| 编号 | 功能 | 说明 |
|------|------|------|
| F-06 | 列出可访问服务器 | 玩家可通过指令查看所有已配置的远程服务器列表及其在线状态 |
| F-07 | 打开共享空间界面 | 玩家通过指令打开指定远程服务器的共享空间，界面外观为类箱子容器（虚拟容器，玩家背包在下方，远程空间物品在上方），**无需客户端安装 Mod**，使用原版容器封包即可 |
| F-08 | 物品浏览 | 玩家可在该容器界面中查看远程空间的物品，悬停查看物品信息 |
| F-09 | 离线数据查看 | 目标服务器离线时，打开的容器展示本地缓存数据，须以视觉方式标注"离线/缓存"（如容器标题标注 `[离线]`），并在容器关闭或操作时提示玩家当前为只读 |
| F-10 | 增量同步 | 打开共享空间时，先向目标服务器查询最后修改时间戳，若与本地缓存的时间戳一致则直接使用缓存，无需传输完整物品列表；不一致时才拉取最新数据 |

### 3.3 物品放入（有权限的玩家）

放入操作在容器界面中通过**鼠标拖拽**完成：玩家从背包栏拖拽物品到容器对应槽位。

| 编号 | 功能 | 说明 |
|------|------|------|
| F-11 | 拖拽放入 | 玩家将物品从背包拖入容器槽位后，物品从玩家背包扣除，向目标服务器发起放入请求 |
| F-12 | 放入-在线校验 | 放入时目标服务器必须在线，否则拒绝操作并将物品退回玩家背包，同时提示 |
| F-13 | 放入-确认反馈 | 放入成功后，容器中对应槽位更新为实际状态；若失败则物品退回并提示原因 |

### 3.4 物品取出（有权限的玩家）

取出操作在容器界面中通过**鼠标拖拽**完成：玩家从容器槽位拖拽物品到背包。

| 编号 | 功能 | 说明 |
|------|------|------|
| F-14 | 拖拽取出 | 玩家将物品从容器拖入背包后，向目标服务器发起取出请求，请求成功后物品进入玩家背包 |
| F-15 | 取出-在线校验 | 取出时目标服务器必须在线，否则拒绝操作并提示 |
| F-16 | 取出-库存校验 | 取出时目标服务器校验物品是否存在、数量是否足够，不足时拒绝并将容器界面恢复为操作前状态，提示玩家 |
| F-17 | 取出-确认反馈 | 取出成功后，容器中对应槽位更新为实际状态；若失败则界面回滚并提示原因 |

### 3.5 跨版本物品兼容

| 编号 | 功能 | 说明 |
|------|------|------|
| F-18 | 兼容物品正常操作 | 不同 MC 版本间能正确解析的物品正常展示，允许放入/取出 |
| F-19 | 不兼容物品展示 | 因版本差异无法解析的物品仍显示在容器槽位中（能渲染则渲染，否则显示占位物品），须以视觉方式标注"不兼容" |
| F-20 | 不兼容物品禁止操作 | 标注为"不兼容"的物品，**禁止**拖拽取出；玩家试图操作时给出提示 |

### 3.6 权限控制

> 首期**不设权限节点**，所有玩家均可查看和操作（放入/取出）共享空间。仅管理员指令（F-01~F-05）需要 OP/管理员身份。
>
> 细粒度权限控制（查看/放入/取出权限节点）标记为未来扩展（见第 6 章）。

### 3.7 通信安全

| 编号 | 功能 | 说明 |
|------|------|------|
| F-21 | 服务器间加密通信 | 所有服务器间的网络通信必须加密，防止中间人窃听 |
| F-22 | 共享空间密码鉴权 | 连接远程服务器时需提供对方共享空间的密码，对方校验通过后才允许访问 |
| F-23 | 密码安全存储 | 本服存储的远程服务器密码及本服自身密码不得明文存放 |
| F-24 | 防重放攻击 | 请求须包含防重放机制，防止攻击者截获并重复发送合法请求 |

### 3.8 操作日志与审计

| 编号 | 功能 | 说明 |
|------|------|------|
| F-25 | 操作记录 | 每次物品放入/取出操作须记录：时间、操作类型、发起玩家（UUID + 玩家名）、目标服务器、物品信息（ID、数量）、操作结果 |
| F-26 | 日志保留 | 日志保留在服务端本地 |
| F-27 | 日志定期清理 | 按配置的保留天数自动清理过期日志，默认 30 天 |
| F-28 | 日志导出 | 管理员可通过指令导出指定时间范围的日志 |

### 3.9 Client-Optional

| 编号 | 功能 | 说明 |
|------|------|------|
| F-29 | 仅服务端可用 | 客户端未安装 Mod 时，所有功能通过指令 + 原版容器界面完成（利用 Minecraft 原版 OpenScreen/HeldItem 等封包） |
| F-30 | 客户端增强 GUI | 客户端安装 Mod 时，打开共享空间时呈现增强界面（服务器列表侧栏、在线状态、最后同步时间、兼容性标记等），核心交互仍为拖拽物品

### 3.10 并发与一致性

共享空间可能同时被本服玩家、外部服务器玩家、多个网络连接和后台同步任务访问。首期必须把一致性作为核心功能处理，而不是后续优化。

| 编号 | 功能 | 说明 |
|------|------|------|
| F-31 | 权威写入方 | 每台服务器只对自己的共享空间库存拥有写入权；远程服务器只能通过协议请求操作，不得直接修改本地缓存 |
| F-32 | 统一写入入口 | 本服玩家访问本服共享空间、外服玩家访问本服共享空间、网络请求和 GUI 操作必须最终进入同一套 `PUT` / `TAKE` 服务端事务逻辑 |
| F-33 | 槽位版本校验 | 每个槽位必须维护版本号；放入和取出请求都必须携带客户端看到的期望版本，服务端在事务内校验后才可提交 |
| F-34 | 原子扣减与发放 | 取出操作只有在权威服务器完成扣减并返回成功后，发起服务器才能给玩家发放物品；失败、超时或冲突时不得生成物品 |
| F-35 | 幂等请求 | 放入和取出请求必须包含全局唯一请求 ID；权威服务器需要记录已处理请求，连接重试或重复包不得导致重复放入、重复取出或重复发放 |
| F-36 | 冲突反馈 | 发生版本冲突时拒绝本次操作，刷新该共享空间缓存，并提示玩家“物品已被其他玩家修改，请重试” |
| F-37 | 放入真实扣除 | PUT 发起时必须先从服务端真实玩家背包扣除物品并进入本服暂存区；不得只依赖 GUI pending 显示 |
| F-38 | 失败发还保障 | PUT 失败、超时、玩家离线或服务器关闭时，暂存区物品必须塞回玩家背包、掉落在玩家位置，或进入离线补偿记录 |
| F-39 | 异步回调校验 | TAKE 成功后的发放回调必须重新校验玩家是否在线、容器是否仍有效；失效时进入掉落或离线补偿流程 |
| F-40 | 不兼容数据保真 | 权威服务器即使无法解析跨版本物品的 `extra_data`，也必须原样保存并原样返回，不得清理或重写未知字节 |

## 4. 指令需求

### 4.1 管理员指令

```
/exchange server add <名称> <地址> <端口> <密码>    — 添加远程服务器（F-01）
/exchange server remove <名称>                        — 删除远程服务器（F-02）
/exchange server list                                  — 列出已配置服务器及在线状态（F-03）
/exchange reload                                       — 热重载配置（F-05）
/exchange log export [天数]                            — 导出操作日志（F-28）
/exchange log clear [天数]                             — 清理指定天数之前的日志（F-27）
```

### 4.2 玩家指令

```
/exchange list                     — 在聊天栏列出可访问的服务器及在线状态（F-06）
/exchange view <服务器名称>          — 打开该服务器的共享空间容器界面（F-07）
/exchange refresh <服务器名称>       — 手动刷新指定服务器的缓存数据
```

- `/exchange view` 打开的界面为原版容器（类似箱子），上半部分为远程空间物品，下半部分为玩家背包。
- 物品的**放入和取出**均在容器内通过鼠标拖拽完成，**不需要额外的 put/take 指令**。
- 玩家拖动物品时，服务端实时校验目标在线状态，离线时操作被拒绝并弹回物品。

## 5. 界面需求

### 5.1 仅服务端安装时的界面（原版容器）

玩家客户端未安装 Mod 时，`/exchange view` 打开的是 Minecraft **原版容器界面**（通过服务端虚拟容器实现）：

```
┌──────────────────────────────────────┐
│  [服务器名称] 的共享空间  [在线/离线]  │   ← 容器标题（含在线状态）
├──────────────────────────────────────┤
│  [槽1]  [槽2]  [槽3]  ...  [槽N]    │   ← 远程空间物品（上排）
│                                      │
│  (不兼容物品以特殊方式标记)            │
├──────────────────────────────────────┤
│                                      │
│  [背包槽1] [背包槽2] ... [背包槽27]   │   ← 玩家背包（下方）
│  [快捷栏1] [快捷栏2] ... [快捷栏9]    │
└──────────────────────────────────────┘
```

| 编号 | 功能 | 说明 |
|------|------|------|
| G-01 | 容器标题 | 容器标题显示服务器名称 + 在线状态（如 `[离线]`） |
| G-02 | 物品展示 | 远程空间物品以原版 ItemStack 形式渲染在容器槽位中 |
| G-03 | 不兼容物品标记 | 不兼容物品替换为占位物品（如屏障方块）并修改显示名称标注"不兼容-物品名"，或通过 Lore 标注 |
| G-04 | 离线只读 | 离线时容器正常打开（展示缓存数据），但所有拖拽操作被拒绝，物品弹回，并提示"目标服务器离线，仅可查看" |
| G-05 | 放入交互 | 玩家拖拽物品从背包到容器槽位 → 服务端发起放入请求 → 成功则物品留在容器中，失败则弹回并提示 |
| G-06 | 取出交互 | 玩家拖拽物品从容器到背包 → 服务端发起取出请求 → 成功则物品留在背包中，失败则弹回并提示 |
| G-07 | 操作反馈 | 拖拽操作因任何原因被拒绝时，物品弹回并聊天栏显示拒绝原因 |

### 5.2 客户端安装 Mod 时的增强界面

客户端安装 Mod 后，打开界面时使用 Mod 自定义的 GUI（利用客户端侧的屏幕渲染），提供更好的浏览体验：

| 编号 | 功能 | 说明 |
|------|------|------|
| G-08 | 服务器导航 | 可在界面内切换查看不同服务器的共享空间，无需关闭/重开（如左侧栏显示服务器列表 + 在线状态指示灯） |
| G-09 | 同步时间 | 界面上显示该服务器数据的最后同步时间 |
| G-10 | 兼容性标记 | 不兼容物品在槽位上叠加醒目的视觉标记（如红色边框、锁图标） |
| G-11 | 快捷操作 | 支持 Shift+点击快速移动整组物品等原版容器操作习惯 |

> **注意**：增强 GUI 仅改善浏览和导航体验，核心交互（拖拽放入/取出）与原版容器界面一致。增强 GUI 也须支持离线缓存浏览和权限受限模式。客户端若无 Mod，降级为 5.1 节的原版容器，功能不缺失。

# 第二部分：参考设计

> 以下为推荐的架构与实现方案，开发者可根据实际情况调整。

## 7. 拓扑结构

采用 **P2P 网状拓扑**——每台服务器对其他所有服务器同时作为客户端和服务端，不存在中心节点。

```
┌──────────┐       ┌──────────┐
│ Server A │◄─────►│ Server B │
└────┬─────┘       └────┬─────┘
     │                  │
     │    ┌──────────┐  │
     └───►│ Server C │◄─┘
          └──────────┘
```

- 每台服务器开放一个 TCP 端口，供其他服务器连接。
- 该端口仅用于**服务器间通信**。
- 玩家不直接连接远程端口——玩家的指令/GUI 由本服 Mod 处理，再由 Mod 向目标服务器发起远程调用。

## 8. 发现与连接

- 管理员添加远程服务器时，须提供：`IP/域名`、`端口`、`对方共享空间密码`。
- 本服自身的显示名称和密码在配置文件中设定。
- 建议为每个远程服务器配置文件级别的别名（即 `/exchange server add` 的 `<名称>` 参数），该名称仅在本服生效，用于指令和 GUI 中的标识。
- 连接建立后，发起方首先发送包含目标密码的认证帧，接收方校验后返回授权结果。认证失败则断开连接。

## 9. 缓存与同步策略

### 9.1 缓存模型

建议采用**拉取 + 推送混合**模式，并利用时间戳做增量同步：

- **增量同步（时间戳）**：每个远程服务器缓存保存最后修改时间戳。玩家打开容器时，先向目标发送"查询修改时间戳"的轻量请求（仅返回时间戳，不含物品数据），若与缓存一致则直接使用缓存，仅在不一致时才请求完整物品列表。放入/取出操作成功后由目标服务器返回新的时间戳并更新缓存。
- **操作触发更新**：玩家放入/取出成功后，直接使用操作响应中的物品数据更新缓存，无需额外拉取。
- **被动推送**（可选）：目标服务器物品变动时推送变更通知给已连接的服务器。
- **手动刷新**：玩家可通过 `/exchange refresh` 或增强 GUI 中的刷新按钮主动触发全量拉取（跳过时间戳比对）。
- **缓存只读**：`remote_cache` 是展示快照，不是库存真相。任何写操作都必须发往目标服务器并由目标服务器事务提交；本地只能在成功响应后更新缓存。

### 9.2 缓存生命周期

- 在线期间：缓存持有最新同步数据。
- 目标离线后：缓存冻结为最后同步的快照，标注离线状态和最后同步时间。
- 建议缓存保留 24 小时，超期可清理。

### 9.3 在线检测

- 服务器间定期发送心跳/Ping（建议间隔 10 秒）。
- 连续 N 次无响应判定离线（建议 3 次，即 30 秒超时）。
- 离线恢复后自动重连并全量同步库存。

## 10. 安全设计

### 10.1 传输层

建议使用 **TLS 1.3** 加密 TCP 连接。证书可为自签名，信任关系通过密码验证替代 PKI。

### 10.2 鉴权流程

```
Client (发起方)                        Server (接收方)
     │                                      │
     │──── TLS 握手 ────────────────────────│
     │──── 认证帧 {目标服务器密码, 时间戳} ──│
     │                                      │── 校验密码
     │◄─── 认证结果 {成功/失败} ────────────│
     │                                      │
     │──── 业务请求 ────────────────────────│
```

### 10.3 防重放

每个业务请求携带**单调递增序列号 + 时间戳**。接收方维护已接收请求的序列号窗口（建议 30 秒滑动窗口），对重复序列号直接丢弃。

### 10.4 密码存储

- 本服密码和远程服务器密码均以哈希形式存储（建议 bcrypt 或 argon2）。
- 配置文件中可存放哈希值或明文（首次加载时自动哈希并覆写）。

## 11. 数据存储

### 11.1 推荐方案：内嵌数据库

| 数据库 | 优点 | 缺点 |
|--------|------|------|
| SQLite | 零配置，广泛使用 | 并发写入能力有限 |
| H2 | Java 原生，支持内存模式 | 社区略小 |

推荐 **SQLite**，数据库文件存放在 `config/the_exchange/data.db`。

### 11.2 备选方案：世界存储

利用 Minecraft 世界的 SavedData 机制持久化。优点是无额外依赖，缺点是性能不如数据库，且难以跨世界共享。

### 11.3 数据表设计（参考）

```sql
-- 本服共享空间的物品
CREATE TABLE exchange_items (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    item_data BLOB NOT NULL,        -- 物品序列化数据
    quantity  INTEGER NOT NULL,
    added_by  TEXT,                 -- 放入者 UUID
    added_at  TEXT NOT NULL         -- ISO 8601 时间
);

-- 远程服务器缓存
CREATE TABLE remote_cache (
    server_name TEXT PRIMARY KEY,
    items_json  TEXT NOT NULL,     -- JSON 序列化的物品列表
    synced_at   TEXT NOT NULL
);

-- 操作日志
CREATE TABLE operation_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp   TEXT NOT NULL,
    op_type     TEXT NOT NULL,     -- PUT / TAKE
    player_uuid TEXT NOT NULL,
    player_name TEXT NOT NULL,
    server      TEXT NOT NULL,     -- 目标服务器名
    item_id     TEXT NOT NULL,
    quantity    INTEGER NOT NULL,
    result      TEXT NOT NULL,     -- SUCCESS / FAIL
    fail_reason TEXT
);

CREATE INDEX idx_log_timestamp ON operation_log(timestamp);
CREATE INDEX idx_log_player ON operation_log(player_uuid);
```

### 11.4 日志清理

建议通过定时任务（如每小时）执行：`DELETE FROM operation_log WHERE timestamp < datetime('now', '-30 days')`，保留天数可配置。

- 核心逻辑抽离为独立模块，纯 Java/Kotlin，不 import 任何加载器特定 API。
- 加载器适配层负责：指令注册、事件监听、配置文件管理、GUI 渲染等。
- 网络和存储模块尽量保持加载器无关。

## 13. MC 跨版本兼容

### 13.1 协议设计

- 服务器间通信使用**自定义中立协议**，不直接传输 Minecraft 的 `ItemStack` NBT。
- 物品序列化为以下最小字段：`{ item_id: String, count: Int, display_name: String, extra_data: Optional<Bytes> }`。
- `item_id` 使用 Minecraft 的 Registry Key 字符串（如 `minecraft:diamond`）。
- `extra_data` 携带 NBT/tag 等额外数据，仅当接收方声明支持时附加。

### 13.2 兼容性判断

- **发送方**负责在序列化时标记物品是否可能在低版本中不兼容。
- **接收方**解析后，对无法识别的 `item_id` 或无法解析的 `extra_data`，标记为"不兼容"并仅展示可用信息。
- 目标服务器（物品存储方）是对物品兼容性的最终判定者。

## 14. 协议选型（参考）

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| 自定义 TCP + 二进制帧 | 轻量，无外部依赖，完全可控 | 需自行设计帧格式、序列化 | 推荐 |
| gRPC | 强类型，自动生成代码 | 依赖较重，可能与 Mod 环境冲突 | 不推荐 |
| WebSocket | 易调试，浏览器友好 | 稍重的头部开销 | 备选 |

建议采用**自定义 TCP + 二进制帧**，帧格式参考：

```
┌─────────┬─────────┬──────────┬──────────────┐
│ Magic   │ Version │ Length   │ Type         │
│ (4B)    │ (2B)    │ (4B)     │ (2B)         │
├─────────┴─────────┴──────────┴──────────────┤
│              Payload (ProtoBuf/MessagePack)   │
└──────────────────────────────────────────────┘
```

- `Magic`: 固定魔数 `0x45584348` ("EXCH")
- `Version`: 协议版本号
- `Length`: Payload 长度
- `Type`: 帧类型（认证、心跳、查询库存、放入、取出、推送等）
- `Payload`: 建议使用 MessagePack 或 Protocol Buffers 序列化

## 15. 并发控制（参考）

同一共享空间可能被本服玩家和多个外部服务器玩家同时操作。库存真相必须归属于物品存储方，其他服务器只保存缓存快照。

- **推荐方案：事务内乐观锁**。放入和取出请求都携带槽位期望版本号；权威服务器在 SQLite 事务内读取、校验、更新和记录日志，提交后返回新版本。
- **幂等请求 ID**。每次玩家操作生成 UUID 级别的请求 ID，权威服务器记录处理结果；重复请求返回第一次结果，不能再次修改库存。
- **单连接串行 + 多连接并发**。同一连接内按序处理请求；不同连接可并发进入业务层，但同一槽位的写入必须通过数据库事务和版本号互斥。
- **冲突处理**。版本不匹配、数量不足或不兼容时拒绝操作，发起服务器刷新缓存并回滚玩家 GUI 操作。
- **备选方案：短事务悲观锁**。仅在 SQLite 写冲突或热点槽位严重时，为单槽位引入短时互斥锁；锁范围不得跨网络等待。

对于 ≤10 台服务器的规模，乐观锁足够。
